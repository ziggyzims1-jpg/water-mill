## Pick up here, in this order

### 1. Review PR #15

Nothing is merged. CI had never run on this branch before the PR opened, so its
check run was the first time `make verify` executed anywhere but the machine
that wrote it — **it passed** (`verify`, 30s, on `0ca7660`). That is the one
part of step 1 already done; the reading is still yours.

The PR body has the decisions worth arguing with. The two most load-bearing, if
you only read two:

- **Queried, never loaded.** The prompt carries no findings — six lines saying
  a `recall` tool exists. If that is wrong, it is wrong in a way that costs
  tokens on every task forever, so it is the thing to push back on now rather
  than later.
- **A proposal is quarantined.** An agent can write a finding; no agent can
  read it until you promote it. That is a deliberate cost — knowledge
  accumulates at the speed of your attention rather than the agent's. The
  alternative was agents writing findings other agents read directly, and the
  reason against it is the task log's own rule: a guess stored in the field a
  judgement belongs in is worse than a blank, because it counts.

### 2. Run the supervised task with `--recall`

**This is the part that is not proven, and it is the reason not to merge on the
strength of a green gate alone.**

```bash
./bin/watermill run zimmy-life-tracker --max-spend 5 --max-tasks 1 --supervised --recall
```

The protocol is tested end to end against real JSON-RPC — handshake,
`tools/list`, `tools/call`, the quarantine, a malformed frame — and the
engine's config-writing is tested against a real git repository. What is **not**
tested is whether `claude -p` accepts `--mcp-config` and `--allowedTools`
spelled the way `engine._recall_args` spells them, and whether an MCP call needs
more than that under `--permission-mode acceptEdits`.

That is precisely the status `land` had before it met a real forge and found a
bug on its first attempt. Same posture: assume it is wrong until one real run
says otherwise.

**What to look at afterwards**, in order:

```bash
cat runs/zimmy-life-tracker/<run-id>/mcp/<task>.json    # what was handed to the agent
cat runs/zimmy-life-tracker/<run-id>/prompts/<task>.txt # does it mention the tool
./bin/watermill recall --usage                          # was it CALLED — the whole question
grep -c mcp__watermill runs/zimmy-life-tracker/<run-id>/tasks/<task>.json
```

`recall --usage` is the answer. It reports every call, the hit rate, and — the
useful half — every question that came back empty. Three outcomes:

| What you see | What it means | What to do |
|---|---|---|
| Calls recorded | The wiring works | Merge; the empty-question list is your first `remember` session |
| Zero calls, task otherwise normal | The agent never reached for it. Either the flags are wrong or the prompt is not persuasive | Fix in **this** PR, not a follow-up |
| Task fails in a new way | The flags are wrong and are breaking the invocation | Same — fix here. `--recall` is off by default, so `main` is unaffected either way |

The graph is empty, so a call will mostly return "Nothing has been recorded
yet." **That is a pass.** The question this run answers is whether the tool is
reachable, not whether it is useful; useful needs findings, and findings need
tasks to have gone wrong first.

### 3. Merge

Only after (1) and (2). If (2) found nothing to fix, merge as-is. The release
workflow reads the PR title, which starts `feat:` — that is a **minor** bump,
which is right.

## What this actually is, in one paragraph

Five modules and one committed JSONL. `knowledge.py` stores findings — dated by
when they were *observed*, append-only, superseded rather than edited.
`recall.py` builds a graph over those plus the task log and the ledger, in
memory, on every call, and answers a free-text query with a handful of one-line
hits under a hard character budget. `mcp.py` exposes that as a stdio MCP server
the agent can call mid-task — the only seam in this orchestrator that runs
*during* a task rather than around one. `review.py` is the monthly sweep over
what the factory believes, plus a `--check` that fails when the sweep itself
stops happening. `usage.py` logs every query so the question "is this feature
worth its tokens" has an answer that is not an opinion.

## Things that would be easy to get wrong

- **Do not seed `knowledge/findings.jsonl` from either CLAUDE.md.** It is empty
  and that is correct. A finding is written after a task has gone wrong; a
  guess is indistinguishable from a lesson once it is in the list, and this one
  is read by agents.
- **Do not put this checkout on a network mount.** The whole no-database design
  rests on `O_APPEND` atomicity, which is a local-filesystem property exactly as
  SQLite's locking is. That is the one deployment that would need a real
  database in front of it.
- **`--recall` stays off by default** until step 2 above passes. A default that
  changes the command every task is sent is not where you discover a flag is
  wrong.
- **A mechanisable rule does not go in the graph.** It goes in the gate or
  `fence.paths`. The graph is the fourth destination and the weakest; the sweep
  names every lesson that stayed advisory, every month, on purpose.
- **The usage log is never readable by an agent.** A tool that can see its own
  usage statistics is a tool with an incentive.

## Open, and yours

- **The empty-question list is the roadmap for the tool schema.** `recall` takes
  free text, a scope and a limit. `--since` and `--cause` exist on the CLI only,
  because every parameter in the agent's schema is paid for on every task. What
  graduates into that schema should be decided by what `recall --usage` shows
  agents actually asking for — not by guessing now.
- **Nothing ships the usage log to Loki.** `shipper.py` sends the ledger and the
  task log. A third stream is a deliberate non-decision, not an oversight.
- **Zero findings, zero recall calls, zero sweeps recorded.** All three counters
  are in `docs/STATUS.md` and all three stay at zero until a task has run and
  something has been learned from it. Same shape as the root-cause counter that
  has been at zero since the two supervised tasks landed — which is still the
  thing blocking everything downstream of Phase 2.

## Command reference

```bash
./bin/watermill recall "a question"              # ask the graph
./bin/watermill recall --detail f-...            # open one answer in full
./bin/watermill recall --usage                   # was the tool called, what went unanswered
./bin/watermill remember <cell> lesson "..." --on YYYY-MM-DD --path <file> --task <id>
./bin/watermill remember <cell> lesson "..." --supersedes f-...  # when it stops being true
./bin/watermill confirm f-...                    # it still holds; resets its clock
./bin/watermill proposals [--promote f-... | --reject f-... --why "..."]
./bin/watermill review [--record | --check]      # the monthly sweep, and its heartbeat
./bin/watermill run <project> --max-spend N --max-tasks 1 --supervised --recall
```
